# Known limitations

- Hermes sessions are minimal and single-turn-per-request: one user message per HTTP request with streamed progress and a persisted reference (see [hermes-sessions.md](hermes-sessions.md)); agent orchestration and hand-off are not implemented.
- Hermes sessions require the installed Hermes executable and a Hermes-configured model provider; without them the Hub reports an honest 503/SSE error state and never simulates a session.
- **Live Hermes execution is opt-in and off by default** (`HUB_HERMES_ENABLED=false`). While disabled, the session endpoints return an explicit `HERMES_INTEGRATION_DISABLED` state and start no subprocess at all. Turning it on only ever launches a local `hermes acp` process under the Hub's own OS user — **this is not equivalent to OS-level sandboxing** (no container, chroot, seccomp profile or filesystem namespace boundary is created by enabling it), and it must never be pointed at school data, production credentials, or anything with access to privileged tools. Treat it as a developer-only, disposable-workspace feature.
- Message content of Hermes sessions is deliberately not persisted (references only); a transcript therefore cannot be replayed from the Hub.
- Permission requests from Hermes tools are always rejected (fail-closed); Hermes may finish such turns with an in-band failure message. Rejecting a `session/request_permission` call stops the Hub from granting ACP-mediated approval — it does **not** prove no tool ran. A session's working directory is an ordinary process `cwd`, not an OS-level sandbox (no container, chroot, seccomp profile, or filesystem namespace boundary is imposed); a Hermes agent process that chooses to ignore the rejection and act outside the ACP tool-call channel is not prevented by the Hub. The Hub only constrains what it controls: the directory is dedicated and kept out of the Hub's own secrets/config tree (`<data_dir>/hermes-workspace`, never the Hub data directory itself), and the subprocess environment is curated to an explicit allow-list (`HERMES_*`, plus ordinary process variables such as `PATH`/`HOME`/`LANG`) so ambient Hub secrets (e.g. `HUB_ADMIN_PASSWORD`) are never exposed to the agent process. True isolation (containers, restricted users, read-only mounts) is out of scope for this integration and would need to be added before any permission boundary here is treated as a security control rather than a best-effort default.
- Hermes session diagnostics (`stderrTail` in `diagnostics`, `agentError.data`, and the persisted `lastError` surfaced via `/api/hermes/sessions` and the SSE error event) are passed through a **best-effort** redaction pass (`hermes_hub_backend/redaction.py`) that scrubs known credential/token/password *shapes* (API-key prefixes, `Authorization`/`Bearer` text, `key=value` assignments, URL-embedded credentials) before they reach an HTTP response, the database, or the audit log. **This is pattern matching, not a guarantee** — a secret that does not match one of those shapes will not be caught. Treat these diagnostic fields as debug-only, do not forward them to third parties, and do not configure a Hermes provider in a way that could print live credentials to stderr in the first place.
- No Ollama/Qwen inference is performed by the Hub itself; the Ollama adapter remains a read-only probe surfaced as `providerContext`.
- **A real end-to-end Hermes↔Ollama/Qwen text exchange has not been run or verified anywhere in this project.** `scripts/hermes-preflight.py` is read-only (executable version, a bare `initialize` handshake with no session created, Ollama reachability/model listing, state-directory existence, Hub config) and does not send any prompt. Actually performing one synthetic-data exchange through the real stack would additionally require: an installed Hermes with a configured model provider pointing at a reachable Ollama instance with the expected model already pulled (the preflight reports, but never changes, any of that); `HUB_HERMES_ENABLED=true` set deliberately for that run; and issuing one request through the Hub's normal authenticated API (`POST /api/hermes/session`) with an obviously-synthetic message, then confirming the SSE stream actually reaches a `done` event and `GET /api/hermes/sessions` shows `status: "active"` with the expected provider/model — not merely that the handshake succeeded. None of this has been attempted in this sandbox (no Hermes or Ollama is installed here, and this project does not install or reconfigure either). Until a human runs that exchange in a real environment and reports the result, do not describe this integration as a verified working Qwen integration — it is an opt-in adapter foundation only.
- No Apps Script application is integrated or deployed.
- Authentication is a single-administrator password-based personal-Hub intent gate, not a multi-user identity system.
- Approval expiry and migration checksums are not implemented in this hardening scope.
- Local snapshots are not off-workspace backups; cleanup retains only the ten newest local snapshots.
- Live restore and every external write fail closed.
- App health status is recorded metadata; registry URLs are never probed by the backend.
- Shared GAS theme/AI protocol is a schema only and is not claimed as deployed.
- Codespaces persistence, private forwarding and HTTPS cookies are configured but not verified on this non-Codespaces host.
- Browser CI requires the pinned Chromium binary and Linux dependencies; local browser execution may be blocked by host policy or network availability.
